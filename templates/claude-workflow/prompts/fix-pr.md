You have been invoked on a pull request via an @claude comment. Take all unaddressed review feedback on this pull request and resolve it fully and autonomously: re-validate each finding against the code, fix the ones that are real, push back on the ones that are not, and for judgment calls derive and implement the best solution. All changes land on the PR branch itself — never open a new pull request. If the triggering comment carries any text beyond a bare mention, treat it as additional scope layered on top of the standard work below.

Phase 1 — Check out the PR branch, refusing fork-based PRs. First determine whether the pull request comes from a fork: run gh pr view on it reading the JSON field isCrossRepository. If that reports true, the PR head branch lives on the contributor's fork, which this job cannot push to — post one short comment with gh pr comment stating that a fork-based PR cannot be fixed in place and that a maintainer must apply the change from a same-repository branch, then STOP. Otherwise run gh pr checkout on the pull request so your working tree is on the PR head branch, and confirm with git status and git rev-parse --abbrev-ref HEAD before making any edits. If checkout fails, post one short comment with gh pr comment explaining the failure and STOP.

Phase 2 — Fetch all unaddressed review feedback from three channels: formal reviews via gh pr view reading the JSON field reviews; issue comments via gh pr view reading the JSON field comments — this is where @claude review output lands, opening with an LGTM or Needs Updates verdict and sections like Needs Fixing; and inline diff threads with resolution state via gh api graphql querying the pull request's reviewThreads with isResolved, isOutdated, path, line, and comment bodies, paginating past the first page if needed. The cutoff is the timestamp of your most recent disposition comment on the PR; with no cutoff, take everything since the PR opened. Collect every review or review-formatted comment newer than the cutoff — if multiple reviews landed, address all of them, not just the latest — and every unresolved inline thread regardless of age, since resolution state, not timestamp, decides whether a thread is open work. Skip DISMISSED reviews, your own prior disposition comments, threads whose last comment is your own disposition reply with no response since, and @claude trigger comments. If there is no feedback to address at all and the triggering comment carried no extra instructions, check whether the PR has merge conflicts (Phase 5); if it does, skip to Phase 5 and resolve them, otherwise post one short comment saying so with gh pr comment and STOP.

Phase 3 — Extract and validate findings. Parse the feedback into discrete, atomic findings tagged Needs Fixing, Requires Human Review, Recommended Optional, or Create Follow-up Issue; classify free-form feedback yourself into the same buckets, split compound feedback into separate findings, and merge duplicates raised by more than one reviewer. A Verification limitation: line is not a finding — skip it when classifying, do not dispose or rebut it, and treat LGTM plus only such lines as approved with nothing to fix. When the only feedback after classification is LGTM plus zero or more Verification limitation: lines and no finding items and no open inline threads and the triggering comment carried no extra instructions: check mergeability; if CONFLICTING or DIRTY go to Phase 5 without posting the short approval comment, otherwise post one short comment with gh pr comment naming each Verification limitation: line when present, or stating the PR is already approved with nothing to fix when not, then STOP — do not post a disposition comment and do not trigger a re-review. The review is a hypothesis, not a work order: a reviewer can cite a stale line, misread a conditional, or flag a non-bug, and implementing a wrong suggestion ships a regression with a reviewer's blessing. For EVERY finding, including ones that read as obviously correct, trace the claim to the current code and assign a verdict: Confirmed — the defect or improvement is real, fix it; Refuted — the code does not do what the finding claims or the suggested change would itself be wrong, do not change and record a one-line code-grounded rebuttal; Partial — real but narrower or broader than stated, fix the true part; Judgment — a real tradeoff the reviewer could not decide. When a Judgment / Requires Human Review finding includes **Recommended proposed solution:**, treat that as the reviewer's preferred option: verify it against the code and the absolute-best standard, implement it if it holds, or implement the better alternative and explain why in the disposition; otherwise derive the most correct and robust solution yourself and implement it, recording the decision and the rejected alternatives — never punt it back and never blind-apply an unverified recommendation. Read the whole function body, not just the cited line. Prove negatives by reading all relevant paths. A suggested remedy is its own claim — verify it is correct for this codebase before applying it, and derive a better fix from first principles if it is not. Any finding touching money, data integrity, security, or an auto-protective mechanism gets fixed or surfaced explicitly, never silently dropped. Scope is a second axis, decided per finding alongside the verdict, against a defined yardstick: the issue or issues the pull request closes — the union of their asks — or, when the pull request closes no issue or its linked issue was deleted, the pull request body's own stated scope. Apply three rules in order; the first match decides — except for a finding the reviewer already routed to Create Follow-up Issue, which is filed and never implemented whatever the rules below would say. Rule 1 is that exclusion's only exception: a defect in code this pull request adds or changes, or a hazard it creates, is fixed here however the reviewer routed it, and the disposition says so. (1) A defect in code this pull request adds or changes, or a hazard THIS pull request itself creates — a new race, a destructive power handed to existing callers — is always in scope, however much mechanism its fix needs, and no later rule or phase may reclassify it; this rule is the safety carve-out in scope form. (2) Otherwise, a remedy that introduces a mechanism the pull request does not have — a new persistent store, a new lifecycle or generation scheme, a new cross-cutting invariant, a retry or recovery path, a new subsystem — which the yardstick does not ask for is out of scope: file it, however small the patch looks. (3) Everything else is in scope, including a pre-existing defect whose remedy needs no new mechanism. The size of the remedy never decides scope in either direction. A Recommended Optional item is a suggestion, not a work order, and carries no authority to enlarge the pull request — run the same rules on it.

Phase 4 — Implement. Fix every Confirmed and Partial finding, implement every Judgment decision (preferring a verified **Recommended proposed solution:** when present) and every Recommended Optional item choosing the most correct and robust design, and file each Create Follow-up Issue item as a GitHub issue with gh issue create using a complete body, never a stub — never implement one, except where scope rule 1 claims it, which is fixed here instead — complexity-prefixed title, problem, goal, approach, acceptance criteria, then a mandatory ## Plain simple English section of under 55 words in ASD-STE100 stating what is wrong and why it matters, then the attribution footer. If the triggering comment carried additional instructions, satisfy them too, scoped as their own item alongside the review findings. Keep each fix scoped to its finding. File each out-of-scope finding as an issue instead of implementing it, and name its number in the disposition comment — a finding you neither implement nor file is a finding you dropped; before filing, search existing issues with gh issue list --search on the finding's keywords with --state all, and cite an existing issue that already covers it instead of filing a duplicate. If implementation reveals that a remedy you classified as in scope cannot work without a new mechanism, re-run the scope rules in order: a rule-1 finding — a defect in code this pull request adds or changes, or a hazard it creates — stays in scope and the mechanism gets built here; a rule-3 finding that turns out to need one moves to rule 2 — stop, file it, and do not build the mechanism. Obey the conventions and invariants documented in CLAUDE.md. Never execute the project's code in this workflow: do NOT run test suites, builds, type checks, simulations, or scripts. Verify by rereading every changed hunk and its call sites; if the repository has CI, it runs checks on the pull request separately. Never weaken a money, data-integrity, security, or privacy invariant to make a change simpler; correctness and safety outrank a smaller diff. A test the fix makes stale follows the repository rule that the optimal solution comes first and the tests follow it: edit an existing test only under one of its three cases (Outdated, Wrong, or Obsolete) and name that case's checkable ground before you touch it; a confirmed finding is the ground for a test its fix makes outdated. A test that breaks in another location is checked before it is edited, judged by reading it since this workflow runs nothing: the refute check runs first, because a broken test may show the finding itself was wrong; when the finding stands, read the test and decide whether it is Outdated (the fix deliberately replaces the tested behavior), Obsolete (the behavior is deleted, or another test covers it), or Wrong (the test was never correct, and passed only because the code shared its defect). One of those is rewritten or removed under that case with its ground. A test that is none of the three means the fix broke real behavior, so leave the test as it is and fix the code. Not every fix needs a new test; write one when it guards behavior that can regress. Never delete, skip, loosen, or narrow a test to reach a green tree; your own reading that a test is wrong is never its own ground. When the correct fix cannot make an ungrounded test pass, do not commit: stop before Phase 6, and report the test with its file and line, what it asserts, and why the fix conflicts with it, in the disposition comment. Disclose every test edit in the commit message and under a Test edits section of the disposition comment: the test, its case, that case's ground, and what the replacement asserts, or the ground alone for a removal.

Phase 5 — Resolve merge conflicts with the base branch. Check the pull request's mergeability via gh pr view reading the JSON fields mergeable and mergeStateStatus. If it reports CONFLICTING or DIRTY, resolve the conflicts on the head branch, never on the base: run git fetch origin followed by git merge origin/<baseRefName> — always merge, never rebase, because the branch is already pushed and reviewed and rebasing rewrites history and breaks inline review threads. Resolve each conflicted file by reading both sides and preserving the intent of both changes — never mechanically take ours or theirs for a whole file. If base-branch changes overlap code you just fixed in Phase 4, re-derive the fix on top of the new base code. If the two sides are genuinely irreconcilable in intent — especially for money, data-integrity, security, or auto-protective logic — do not guess: post one short comment with gh pr comment explaining the irreconcilable conflict and STOP. After resolving, reread every merged hunk and its call sites just as in Phase 4.

Phase 6 — Commit, push, and verify the push landed. Stage only the files you changed — never a blanket add (a merge commit from Phase 5 stages its own resolution; commit it as git created it). Commit following the repository commit conventions and push to the PR branch with git push origin HEAD. Then confirm the push actually updated the pull request: read the PR head commit via gh pr view reading the JSON field headRefOid, and compare it to your local HEAD from git rev-parse HEAD. If they do not match, post one short comment with gh pr comment reporting that the change did NOT land on the pull request and STOP without claiming success.

Phase 7 — Post one disposition comment with gh pr comment telling the reviewer exactly what happened to each finding, written as direct scannable status with a file and line anchor per item, and with each finding title copied verbatim from the review comment, word for word and never paraphrased or shortened, because the next review reads these dispositions and matches its findings to them by claim: a Fixed section whose every item that kept a finding in the pull request against something that would have filed it — the reviewer's Create Follow-up Issue routing, or your own rule 2 — names scope rule 1 and states from code what this pull request adds, changes, or endangers that makes the rule match, while every other Fixed item overrides nothing and carries no such note, a Corrected scope section for Partial findings, a Not changed section carrying the code-grounded rebuttal for each Refuted finding, a Resolved judgment calls section stating the implemented solution and the rejected alternatives so a human can override after the fact, a Resolved merge conflicts section listing each conflicted file and how the two sides were reconciled, and a Deferred to follow-up section whose every item names both its basis and the issue filed — the basis is either the scope rule you applied, or the reviewer's own Create Follow-up Issue routing for an item the Phase 3 exclusion filed without running a scope rule on it — and that pair is the deferral's rationale, it is what settles the finding for the next reviewer, and a deferral missing either half settles nothing, so the same blocking finding returns next cycle. Omit empty sections. If ALL findings were refuted, still post the disposition comment with the rebuttals — never silently no-op.

Phase 8 — Trigger a re-review as a SEPARATE comment posted after the disposition comment, whose entire body is one trigger line and nothing else. If the addressed set contained only non-blocking items (Recommended Optional or follow-ups, no Needs Fixing or Requires Human Review findings), make the body the three words @claude sonnet review; such a pass consumes no rung. Otherwise the blocking trigger is keyed to the reviewer that actually ran cycle 1, and the score band does not decide it — the band only ever selected that reviewer. First identify the cycle-1 reviewer: list the pull request's comments in chronological order and take the EARLIEST one whose entire body is an @claude … review trigger line, skipping every @claude sonnet review comment unless the pull request's band is C0 to C10. Skip the sonnet comments because a non-blocking pass posts that same phrase at any band and a first review can arrive with no trigger comment at all — a human reviewer, or a run that found feedback already present and posted nothing — so on a C90 pull request the earliest trigger comment can be a non-blocking @claude sonnet review, and reading it as cycle 1 would pin every later blocking re-review to the cheapest reviewer. Inside C0 to C10 the skip changes nothing, because the band posts that same phrase as its first review. If that cycle-1 trigger names fable — @claude fable review at any score, whether the C81 and above band selected it or a stamped PR review: line in the linked issue's Execution block named Fable at any score — the reviewer steps down one rung per blocking re-review, because a Fable first review only ever runs once and its trigger is never repeated: post the three words @claude opus review when no @claude opus review comment follows that fable comment, and the two words @claude review once a step-down to opus has already happened. That ladder stops at @claude review and never steps down to sonnet. If the cycle-1 trigger names any model other than Fable, a first review on any model other than Fable keeps its own trigger for every blocking re-review: repeat that same trigger line verbatim, whatever the band — a [C5] pull request whose cycle 1 was @claude opus review posts @claude opus review at cycle 2 and again at cycle 5, and a [C90] pull request stamped @claude opus review carries no fable trigger comment and still posts @claude opus review, never the band's bare @claude review. Only when the pull request carries no cycle-1 trigger comment — no @claude … review comment at all, or none left after the non-blocking sonnet comments are skipped — does the band decide, read from the [C<score>] bracket in the pull request title, or from the [C<score>] prefix of the issue it closes when the title carries none: the three words @claude sonnet review at C0 to C10, the two words @claude review at C11 to C40, and the three words @claude opus review at C41 to C80, at C81 and above, and when no score is available — a first review already happened by some other route, so never open a Fable cycle on a re-review. Never bundle this trigger into the disposition comment — it must be its own comment or the re-review will not fire.
