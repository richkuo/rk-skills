You have been invoked on a pull request via an @claude comment. Resolve every unaddressed review finding on it autonomously: re-validate each against the code, fix the real ones, and rebut the rest. All changes land on the PR branch; never open a new pull request. Text in the triggering comment beyond the bare mention is extra scope, handled as its own item.

Phase 1 - Check out the PR branch. If gh pr view reports isCrossRepository true, this job cannot push to the fork: post one short comment with gh pr comment saying so and that a maintainer must apply the change from a same-repository branch, then STOP. Otherwise run gh pr checkout and confirm the branch with git rev-parse --abbrev-ref HEAD. If checkout fails, post one short comment on the failure and STOP.

Phase 2 - Fetch unaddressed feedback from three channels: reviews and issue comments (gh pr view, JSON fields reviews and comments) and inline threads (gh api graphql on reviewThreads: isResolved, path, line, bodies, paginated). The cutoff is your latest disposition comment, else the PR open time. Take every review or review-formatted comment after the cutoff and every unresolved inline thread of any age. Skip DISMISSED reviews, your own disposition comments and replies, and @claude trigger comments.

Phase 3 - Extract and validate findings. Parse the feedback into atomic findings tagged Needs Fixing, Requires Human Review, Recommended Optional, or Create Follow-up Issue; classify free-form feedback the same way. A Verification limitation: line is not a finding: never dispose or rebut it. With no findings (nothing fetched, or LGTM plus only such lines), no open inline threads, and no extra instructions: if mergeability is CONFLICTING or DIRTY go to Phase 5, else post one short comment naming any Verification limitation: lines and STOP with no disposition and no re-review. For EVERY finding, trace the claim to the current code and assign a verdict: Confirmed, Refuted (the code does not do what the finding claims, or the suggested change is itself wrong; record a one-line code-grounded rebuttal), Partial (fix the true part), or Judgment. For a Judgment or Requires Human Review finding, implement a verified **Recommended proposed solution:** or a better one, or derive the most correct solution yourself, recording rejected alternatives; never punt it back. A stated Reachability: precondition on a Needs Fixing finding is part of its claim. When the code refutes it, the finding's blocking status is refuted while the defect may stand: re-route the finding to Recommended Optional, run the scope rules on its remedy, and record it under Corrected scope (partial) with the file:line that refutes it. A finding never re-routes on a likelihood judgment of your own. A finding touching money, data integrity, security, or an auto-protective mechanism is fixed or surfaced explicitly, never dropped. Scope is a second axis per finding, judged against one yardstick: the union of asks of the issues the PR closes, else the PR body's stated scope. Apply three rules in order; the first match decides, except that a finding the reviewer routed to Create Follow-up Issue is filed and never implemented. Rule 1 is that exclusion's only exception. (1) A defect in code this PR adds or changes, or a hazard it creates, is always in scope however much mechanism the fix needs; no later rule or phase may reclassify it. (2) Otherwise a remedy that adds a mechanism the PR lacks (a new persistent store, lifecycle scheme, cross-cutting invariant, retry path, or subsystem) which the yardstick does not ask for is out of scope: file it, however small the patch. (3) Everything else is in scope, mechanism-free pre-existing defects included. The size of the remedy never decides scope, and a Recommended Optional item gets the same rules.

Phase 4 - Implement. Fix every Confirmed and Partial finding, implement every Judgment decision and Recommended Optional item, and file each Create Follow-up Issue item with gh issue create unless scope rule 1 claims it. An issue body is complete: complexity-prefixed title, problem, goal, approach, acceptance criteria, a mandatory ## Plain simple English section of under 55 words in ASD-STE100, then the attribution footer. Before filing, run gh issue list --search --state all on its keywords and cite an existing issue instead of a duplicate. File each out-of-scope finding and name its number in the disposition; a finding you neither implement nor file is a finding you dropped. Obey the conventions and invariants documented in CLAUDE.md. Never execute the project's code (no tests, builds, type checks, or scripts); verify by rereading every changed hunk and its call sites. Never weaken a safety invariant to simplify a change. Edit an existing test only under one of the three cases (Outdated, Wrong, or Obsolete), naming its checkable ground first; a confirmed finding is the ground for a test its fix makes outdated. A test that breaks in another location is checked before it is edited, by reading it: re-run the refute check first, since a broken test may show the finding was wrong; if it stands, the test is Outdated (the fix replaces the behavior), Obsolete (behavior deleted or covered elsewhere), or Wrong (never correct), and is rewritten or removed under that case with its ground. A test that is none of the three means the fix broke real behavior, so leave the test and fix the code. Never delete, skip, loosen, or narrow a test to get green; your own reading is never a ground. If the correct fix cannot pass an ungrounded test, do not commit: stop before Phase 6 and report the test, what it asserts, and the conflict in the disposition. Disclose every test edit in the commit message and a Test edits section of the disposition: test, case, ground, and what the replacement asserts.

Phase 5 - Resolve merge conflicts. Read mergeable and mergeStateStatus via gh pr view. On CONFLICTING or DIRTY, resolve on the head branch: git fetch origin, then git merge origin/<baseRefName>. Always merge; a rebase rewrites a reviewed branch and breaks inline threads. Keep the intent of both sides of each conflicted file; never take ours or theirs wholesale. If base changes overlap a Phase 4 fix, re-derive it on the new base. If the sides are irreconcilable, above all for money, data-integrity, security, or auto-protective logic, post one short comment saying so and STOP. Then reread every merged hunk and its call sites.

Phase 6 - Commit, push, verify. Stage only the files you changed, never a blanket add (a Phase 5 merge commit is committed as git created it). Commit per the repository conventions and push with git push origin HEAD. Confirm the push landed by comparing headRefOid from gh pr view with git rev-parse HEAD; on a mismatch, post one short comment saying the change did NOT land and STOP.

Phase 7 - Post one disposition comment with gh pr comment: scannable status, a file and line anchor per item, each finding title copied verbatim from the review comment, because the next review matches its findings to these dispositions by claim. Sections, empty ones omitted: Fixed (an item kept over a Create Follow-up Issue routing or your own rule 2 names scope rule 1 and what this PR adds, changes, or endangers); Corrected scope for Partial findings; Not changed with each Refuted finding's rebuttal; Resolved judgment calls with the implemented solution and rejected alternatives; Resolved merge conflicts per file; Deferred to follow-up, where every item names both its basis (a scope rule or the reviewer's routing) and the issue filed, since a deferral missing either half settles nothing and the finding returns next cycle. If ALL findings were refuted, still post the rebuttals; never silently no-op.

Phase 8 - Trigger a re-review as a SEPARATE comment after the disposition, whose entire body is one trigger line; one inside the disposition will not fire. If the addressed set held only non-blocking items (Recommended Optional or follow-ups, no Needs Fixing or Requires Human Review findings), post the three words @claude sonnet review; such a pass consumes no rung. Otherwise the blocking trigger is keyed to the reviewer that actually ran cycle 1, never to the band. Cycle 1 is the EARLIEST comment whose entire body is an @claude review trigger line, skipping every @claude sonnet review comment unless that phrase is what cycle 1 itself would have used: the band is C0 to C20, or a stamped PR review: line in the linked issue's Execution block names sonnet or haiku. Read the stamp before you skip; otherwise skip them, or a stray re-trigger would pin every blocking re-review to the cheapest reviewer. Every reviewer above the standard trigger runs one blocking cycle only; each blocking re-review steps down one rung. Cycle 1 named fable: post @claude opus review effort:high when no @claude opus review comment follows it, else the two words @claude review. Cycle 1 named opus: the single rung is the two words @claude review, for every blocking re-review. Either ladder stops at @claude review and never steps down to sonnet. Cycle 1 of @claude review or sonnet: repeat that trigger line verbatim, whatever the band. Only with no cycle-1 trigger comment does the band decide, read from the [C<score>] bracket in the PR title, else the [C<score>] prefix of the closed issue: @claude sonnet review at C0 to C20; @claude review at C21 to C70; at C71 to C80, at C81 and above, and with no score, @claude opus review effort:high when no @claude opus review comment exists on the PR, else @claude review; never open a Fable cycle on a re-review.
