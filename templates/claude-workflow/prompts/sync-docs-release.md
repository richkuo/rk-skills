A repository maintainer comment invoked you. The final sentence appended to this prompt names the operation mode: sync-docs, create-release, or sync-release. Execute exactly that mode. Rules for every mode:

Before any git log range or tag inspection, run git fetch --tags --force, and if the clone is shallow, git fetch --unshallow (a report that there is nothing to do is success). Only then trust baseline..HEAD ranges and tag listings.

Documentation-sync procedure (run first in sync-docs and sync-release mode):

1. Baseline: use git log to find the most recent docs-sync commit and record its short hash. A docs-sync commit has a docs or docs(scope) subject that begins with sync, a docs(sync) scope, or a subject that begins with sync docs; a commit that mentions sync docs later in its subject, or a docs commit that only names CLAUDE.md or SKILL.md does not count. When that commit's body, or the body of the pull request named by a (#N) suffix in its subject (read with gh pr view), holds a Docs-sync-range-end: <sha> line and that sha is an ancestor of HEAD, use that sha as the baseline instead of the commit, because a squash merge lands the sync commit after commits merged while its pull request was open. If none exists, review the last ten commits, pick a sensible starting point, and state your choice.
2. Record the range end with git rev-parse HEAD. List commits in the baseline..HEAD range with git log --oneline. Ignore pure CI, workflow, and chore commits unless they change agent-facing behavior.

4. Sync bidirectionally: add what is new, and delete or correct any statement the code now contradicts (stale paths, renamed symbols, removed fields, dead defaults). Verify a claim against the code before deleting it; never remove a claim you have not confirmed is wrong.

6. Run wc -c on CLAUDE.md. If it exceeds 40000 bytes, condense it in place to under 38000 bytes without splitting it into multiple files.

Then follow the branch and pull-request procedure for the current mode.

- Determine the next semantic version: list tags with git tag --sort -v:refname, review the commits since the latest tag, and state the bump rationale in plain words (breaking change is major, new feature is minor, fixes or polish are patch).
- Confirm git status as in sync-docs mode.
- Branch: git checkout -b docs-release/v<version>, for example docs-release/v1.2.3. If the repository has no such merge-triggered release workflow, stop and post a comment saying so.
- Commit only the documentation files with a message whose subject begins with docs: sync, whose body holds the line Docs-sync-range-end: <the recorded HEAD sha>, ending the message with the standard attribution footer. git push origin <branch>, then gh pr create with base main and a title that begins with the same docs: sync subject. The body carries the same Docs-sync-range-end line and states the exact version that will be published, the bump rationale, a preview of the release notes, and a warning line that merging publishes that release and closing without merging publishes nothing. Report the pull-request URL and stop.
- Create no tag and publish no release yourself. The human merge is the only release gate.

create-release mode publishes a release immediately from the current main tip. This is real and irreversible.

1. Preconditions: git status is clean, and HEAD equals the tip of origin main by SHA (the checkout may be detached-HEAD). Run git fetch origin main, then compare git rev-parse HEAD with git rev-parse origin/main. If they differ, stop and post a comment saying the checkout is not on the current tip of origin main.
2. Inspect tags with git tag --sort -v:refname and review the commits since the latest tag with git log.
3. Determine the semantic version bump and state the rationale in plain words, as above, and name the bump category the commits require. Before you settle on it, read the manifest versions with the discovery and classification rules of step 4. When every applicable field resolves to one value V, and V is the next patch, minor, or major version after the latest semver tag, release V instead and state that the manifests chose it, but only when the bump category of V is at least the category the commits require (major above minor above patch). When V is a smaller bump, stop before step 5, create no tag, and post a comment that names V, the required category, and the commits that require it. When no semver tag exists, release the value the fields resolve to. A pubspec.yaml value counts without its + suffix. When the fields do not resolve to one such V, keep the bump from the commits. This mode edits no file and makes no version-bump commit.
4. Verify the manifest versions against the release version before you publish. The check runs on the checked-out commit that step 1 proved equal to the tip of origin main. The release version is the X.Y.Z from step 3, and a manifest value matches only when it equals X.Y.Z without the v prefix. The one exception is pubspec.yaml: compare only the part before any + suffix, because that suffix is a build number this check never reads.
- Discover the version fields with Glob, then read each file in full. The manifests and fields are: package.json "version"; .claude-plugin/plugin.json "version"; app.json, app.config.js, and app.config.ts expo.version; pubspec.yaml version; Cargo.toml [package] version; pyproject.toml [project] version or [tool.poetry] version; iOS *.xcodeproj/project.pbxproj MARKETING_VERSION; Android build.gradle versionName. Manifests in the repository root directory are always applicable. A nested manifest (any file below the root, for example a workspace package or an app in a subdirectory) is applicable only when it holds the version of the latest semver tag or the release version (in step 3, the value the root manifests hold). When no root manifest holds a resolved version, a nested manifest is also applicable when its value is higher than the version of the latest semver tag, because a merged bump PR may have moved only the nested packages. With no semver tag, every nested manifest is applicable. Name each nested manifest that is not applicable, with its value and the reason, in the comment or report you post at the end of this mode. Skip vendored, generated, fixture, and example directories such as node_modules, test/fixtures, and examples. Schema and config versions (for example version: 2 in .github/dependabot.yml) and native build numbers (buildNumber, versionCode, CURRENT_PROJECT_VERSION) are outside this check.
- Classify each field. Matching: the value equals X.Y.Z (for pubspec.yaml, the part before any + suffix equals X.Y.Z, so 1.4.0+23 matches 1.4.0 and 1.3.9+23 does not). Mismatched: a literal value that differs from X.Y.Z under that comparison. Absent: the file was read in full and holds no version field. Unresolved: the file cannot be read, is malformed, computes the version dynamically (for example from code, an environment variable, or a function call), inherits it from a file you did not read in this pass, or holds ambiguous values. A read failure is never an absent field. An inherited value is resolved only when the file that defines it was read in this pass and holds a literal. Two standard derivations are the exception. A Flutter build value of flutter.versionName or flutterVersionName (Android build.gradle versionName) or $(FLUTTER_BUILD_NAME) (iOS MARKETING_VERSION) inherits from pubspec.yaml: when pubspec.yaml was read in this pass, the field takes its pubspec value before any + suffix and is classified by that value. A pyproject.toml is outside this check, because its version comes from the release tag, when its version is listed in dynamic and the file names a version-control backend such as setuptools-scm or hatch-vcs, or when it has a [tool.poetry-dynamic-versioning] table with enable = true (its [tool.poetry] version is then only a placeholder). Every other dynamic value stays unresolved.
- Use only your Read, Glob, and Grep tools for discovery and inspection. Do not use shell git show, a parser command, or any other shell command to read a manifest. Never run repository code, application configuration, or a package-manager or build command to obtain a version.
- Continue to step 5 only when discovery proved that no applicable version field exists, or every applicable field is matching. Absent fields do not block publication.
- On any mismatch, stop before step 5, create no tag, and post a comment that lists each affected file with its current value and the expected value X.Y.Z. State that a separate version-bump pull request must merge to main before create-release runs again. Never recommend sync-release as the bump mechanism, because its commit holds documentation only.
- On any unresolved value, stop before step 5, create no tag, and post a comment that names each affected file and the reason verification failed. When mismatches and unresolved values both exist, report both in one comment.
5. Never create or push a git tag yourself; you have no push capability in this mode. Record the full hash from git rev-parse HEAD, which is the commit that step 4 inspected, then run one command: gh release create v<version> --target <that hash> --title v<version> --generate-notes.
