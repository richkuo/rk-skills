# work-on-issue

Take the selected issue to a verified, open pull request (PR). Follow the repository's AGENTS.md/CLAUDE.md for engineering, test edits, attribution, and Response Style. Do not pause to ask the user; report at the end. Stop and report only when a gate fails or an unresolved requirement prevents safe progress. Review triggers, review cycles, merge, deployment, and follow-on issue creation belong to the caller.

## Input

Accept an issue number, URL, `owner/repo#N`, or `{ issue, targetBranch?, baseRefs?: [{ pr, ref, sha }, ...] }`. With no identifier, use the issue validated or planned this session; with none, stop and ask which issue. Never select an issue from `gh issue list` or any other list. `targetBranch` also accepts prose such as "target branch develop". `baseRefs` pins reviewed predecessor heads in caller order.

## Run record

Keep a run record at `<root>/.claude/worktrees/run-records/<owner>-<repo>-issue-<N>.json`, where `<root>` is the repository's primary worktree: the parent of `git rev-parse --git-common-dir`, resolved to an absolute path before any tool changes the working directory. Read and write it by that absolute path from the main checkout and from inside the worktree alike; the harness scratchpad is the fallback only when the repository forbids untracked files under `.claude/`. It is never committed and never staged. It holds repository, issue, target, base commit, ordered dependency pins, plan source, worktree path, branch, verification results, and the published commit and PR URL. Update it after every durable step so a retry can inspect completed work before repeating a mutation.

When the record is missing, the branch itself is the evidence: the issue reference in each commit subject attests the issue; `git merge-base --is-ancestor <target commit> HEAD` attests the target; the per-pin ancestry check in dependency-base.md attests the pins; an open PR's body attests all of them. Commit footers attest the harness only. Step 1 discards a record whose PR is merged or closed, or whose worktree path no longer exists, and rewrites it from the current run; nothing else deletes records.

## Steps

### 0. Resolve the issue, gate-check it, and detect a plan

Resolve the repository and issue together. Confirm the clone's fetch and push remotes match the intended repository; use a matching clone for another repository. Pass `-R <owner>/<repo>` to every `gh` command. Run `gh issue view <N> -R <owner>/<repo> --comments` and read the full body, every comment (paginate when truncated), and the repository instructions before any mutation.

Gates: the issue must be open, and no open PR may already fix it. Run `gh pr list -R <owner>/<repo> --state open --search "#<N> in:title,body"` and inspect `gh issue view <N> --json closedByPullRequestsReferences`; open each candidate and check whether it actually fixes the issue (a passing mention does not count). A failed lookup blocks. If another PR already fixes the issue, stop with its URL. This run's own PR does not count; step 1 resumes it after verifying repository, head, base, and worktree.

Detect a plan from a comment starting with `## Implementation plan` (any parenthetical model tag), or one a maintainer or caller clearly frames as a plan. Unless the user explicitly selects one, adopt the newest applicable posted plan, even over a caller-supplied plan; use the caller's plan only when none is posted. Earlier plans are superseded, never merged. Record the adopted plan's author, URL or local source, date, and whether a Fable 5.1 model authored it (heading or footer). Step 6's `, fableplan` marker keys on that flag. No plan is normal.

Honor an explicit build model/harness assignment. A driver dispatching a stamped Codex or Cursor build must load `cli-dispatch`; an already-dispatched builder continues here without dispatching itself again. Report unavailable or substituted models through that contract.

### 1. Create the isolated worktree on a verified base

**Target.** Resolve `targetBranch`, else `gh repo view -R <owner>/<repo> --json defaultBranchRef -q .defaultBranchRef.name`, once. Before shell use, the name must match `^[A-Za-z0-9][A-Za-z0-9._/@+-]*$`, contain no `..`, carry no `refs/` prefix, and pass `git check-ref-format --branch`. `git ls-remote --heads origin "refs/heads/<target>"` must return exactly that one ref (a bare name tail-matches `release/<target>`). Run `git fetch origin <target>` and record the commit of `origin/<target>`. A missing or invalid target blocks; never substitute another branch. Keep this target through publication, even if the default later changes.

**Base.** Without `baseRefs`, use the fetched target commit. With `baseRefs`, read [dependency-base.md](dependency-base.md) and validate the entire list before creating or changing a worktree.

**Name.** Branch and worktree: `<prefix>/issue-<N>-<slug>`, with `cc/`, `cursor/`, or `codex/` for the active harness. `<slug>` is the issue title lowercased, non-alphanumeric runs replaced by one hyphen, trimmed to the first 5 words. The name is deterministic so a retry finds the same worktree.

**Resume or create.** Inspect `git worktree list --porcelain`, `git branch --list '*/issue-<N>-*'`, and `git ls-remote --heads origin "refs/heads/*/issue-<N>-*"` for any existing worktree or branch for this issue, local or remote, under any prefix. At most one worktree and branch exists per issue. On a remote-only hit, fetch it and apply the same attribution check: resume onto it in a worktree created from that branch, else stop. If one exists, check the run record (after the discard rule above), the branch evidence the run-record section names, and any open PR for this run's repository, issue, target, and dependency pins. Reuse only work attributable to this run with the same target and pins; a matching name alone proves nothing. Ambiguous ownership, changed pins, unrelated work, or an unfinished Git operation (a `MERGE_HEAD`, rebase, or cherry-pick in progress) stops the run with the worktree path and the evidence; never create a second worktree for the same issue and never delete, reset, or clean the existing one. On resume, verify the recorded base is an ancestor of `HEAD`; implementation commits need not equal the base.

For a fresh run on Claude Code: `EnterWorktree(name: "cc/issue-<N>-<slug>")`; if the tool altered the branch name, `git branch -m cc/issue-<N>-<slug>`. `EnterWorktree` always branches from the default branch, so on a brand-new, commit-free worktree whose `HEAD` differs from the resolved base, run `git -C <worktree-path> reset --hard <resolved-base>`. Cursor and Codex: `git worktree add .claude/worktrees/<prefix>/issue-<N>-<slug> -b <prefix>/issue-<N>-<slug> <resolved-base>`, then `cd` in. Use the repository's own worktree location when it defines one. Confirm `HEAD` equals the resolved base commit. Never implement on the target branch or in the main checkout. Anchor every later command with `-C <worktree-path>`; shell state does not persist between calls. Write the run record now.

### 2. Understand the issue and the code

Trace affected paths and map every acceptance criterion, including negative requirements, to an observable check. Read validation findings and the repository docs for the touched subsystem. Resolve implementation details from the code and validation evidence while preserving the requested outcome. If validation marked the issue's sketch as doubtful or wrong, or it conflicts with the code, implement the optimal direction for this repository and note the discrepancy in the PR body. If the issue is already satisfied, report the evidence without an empty PR; if its goal is ambiguous or infeasible, report the blocking decision.

**An adopted plan is the blueprint**: implement to it instead of re-deriving. Three overrides, in order: (1) **the traced code**: where the plan contradicts what the code does, follow the code; (2) **anything newer on the issue**: a later maintainer comment or edit supersedes the part it touches; (3) **correctness and safety**: a plan step that breaks an invariant is wrong. When two overrides conflict, the higher-numbered one wins: a newer comment beats the traced code, and correctness and safety beat both. Existing behavior informs implementation; it does not cancel a requested behavior change or an acceptance criterion. Name every deviation in the PR body with its reason. This is the single plan-deviation policy; a caller restatement never narrows it, and a caller sentence permitting one override does not remove the other two. Explicit user requirements remain authoritative.

**Mirror the plan's steps into the task tracker** (`TodoWrite` or equivalent) before writing code, one item per step; mark an item complete only when its verify point passes. Derive missing numbering or per-step observable checks yourself. Without a tracker, keep the checklist in the run record. An overridden step closes as a recorded deviation carrying its own verify point (or the superseding comment) and a matching PR-body entry; it is never marked done and never left open. A borrowed verify point re-homes when its source step is overridden: to the replacement's verify point, else the item's own observable check, else the item closes as its own recorded deviation; re-homing cascades through borrowers of that item's check. No open item may wait on a check that can never run. Without a plan, track the acceptance checks directly.

### 3. Implement the fix

Build the best solution per the repository's engineering rules: follow existing conventions, respect invariants, keep the diff scoped to the issue, and update documentation the change makes stale. Write tests for behavior that can regress. For a bug fix, prove the regression test is real (red then green) by running it against the unfixed base first, in a way that preserves the current work (a stash or a second checkout); if reproduction is unavailable, state the limitation. Documentation-only changes need relevant validation, not artificial runtime tests.

The repository's test-edit rules own stale-test edits: the cases Outdated, Wrong, and Obsolete, each with a named checkable ground, disclosed in the commit and PR body. A test with no ground stays as it is and the code gets the fix. A test that breaks in another location is checked before it is edited: classify it as Outdated, Wrong, or Obsolete and edit under that case with its ground; a test that is none of the three means the change broke real behavior, so fix the code. If the correct change still cannot pass an ungrounded test, stop before step 5, keep the worktree, and report it (step 7).

### 4. Verify before claiming anything

Run the project's build, tests, and linters (per its `CLAUDE.md`, `package.json`, or Makefile) plus the acceptance checks from step 2. Review the complete diff against the recorded base for omissions, unrelated changes, and unintended generated files. Close every plan item with evidence or a recorded deviation.

Fix failures caused by this change. Check an alleged pre-existing failure against the unchanged base before labeling it. Required checks that fail block the commit and PR path. Checks that cannot run block too, with one exception: a caller instruction that forbids executing the project's code and defers checks to continuous integration (CI), such as the issue-workflow prompts' "do NOT run test suites" line, authorizes publication, and the PR body must then state which checks did not run locally. Record commands, results, and tested state in the run record; rerun affected checks after later edits. Local success does not establish CI success.

### 5. Commit and push

Review `git status` and the staged diff before staging; `git add -A` only when nothing unrelated appears, otherwise stage intended files by name. Commit with the repository's title convention referencing the issue, ending with the LLM Attribution Footer (`Created`; `<harness>` is `Claude Code` interactively, or the GitHub Action identifier in CI) for the actual builder. Confirm the final commit contains the verified changes. Push with `git push -u origin <branch>` and confirm `git ls-remote origin refs/heads/<branch>` equals the local `HEAD`. Never force-push to repair a mismatch. After an uncertain push, inspect remote state before retrying. Record the commit in the run record.

### 6. Open the PR

Re-run the step 0 duplicate-PR search and issue-state check, re-check that `origin/<target>` still exists, and with `baseRefs` recheck the pins per dependency-base.md. If a gate changed, preserve the branch and report it. Set `--base` to the recorded target. Read `gh pr list --head <branch> --state all`. An open PR from this run is verified and updated instead of creating another. A merged PR means the work already landed: stop and report it. A closed, unmerged PR is not this run's PR: clear the record's PR fields and create a new one; never reopen it. After an uncertain create response, search for the exact head/base pair before retrying.

Title: the repository's PR-title convention (CLAUDE.md default); append `, fableplan` only when the step 0 Fable flag is set or a Fable 5.1 plan produced this session drove the build; a maintainer's plan earns no marker. Body: `Closes #<N>`; `## Summary` and verification first, naming any checks that did not run locally; every test edit disclosed per CLAUDE.md; the adopted plan linked with every deviation and its reason (or "none"); with `baseRefs`, the predecessor PRs and verified heads in order, stating they must merge first (the PR base stays the target branch); with a non-default target, a `Target branch:` line; `## Plain simple English` last before the attribution footer, per Response Style. Send multiline text through `--body-file` or a structured tool argument. Leave issue closure to the merge.

Read back the PR with `gh pr view <url> --json state,headRefName,headRefOid,baseRefName,body` and verify repository, open state, head branch and commit, base, and body. Return success only when the remote head matches the verified local commit and the requested change is present in the PR diff. Record the PR URL.

### 7. Report to the user

The skill ends here; the caller triggers any `@claude` review and waits on CI. Report the worktree/branch, the target branch when it differs from the default, what was implemented, the verification result, the commit SHA, and the PR URL. On a blocker, state the stage, the evidence, the preserved worktree, and which commit, push, or PR already exists; check the run record and branch before claiming no commit exists, since dependency integration or an earlier attempt may have committed. When step 3 stopped the run on an ungrounded failing test, name the test with its `file:line`, what it asserts, and the conflict, and state whether any commit or PR exists. Name follow-on work the deliverables mention as unfiled. Return caller-required structured fields from verified state. Cap the report at 55 words, plain simple English in ASD-STE100, per the Response Style rules.
